## 3. 絶対ゲート

この仕様に外部入力、外部通信、課金、公開、送信、外部変更、重い実行が含まれる場合、必ず次の順序を実装する。

```text
Security Gate
→ Cost / Consequence Gate
→ 明示的な1回限りの承認
→ 承認範囲内の実行
→ 結果確認・監査記録
```

後段のゲートで前段を代替してはならない。

### 必須防御

- [ ] 拡張子と実体の不一致を拒否
- [ ] パスとファイル名を内部IDへ正規化
- [ ] パストラバーサルと制御文字を拒否

- [ ] 合格入力のハッシュを記録
- [ ] 実行直前にハッシュを再確認
- [ ] 可能な場合は安全な制限形式へ再エンコード

## 6. Approval Gate仕様

承認は次へ固定する。

- Security Gateの入力ハッシュ
- 実行対象
- 利用先とアカウント
- 実行条件
- 料金上限
- 外部への影響
- 有効期限
- 1回限り

入力・条件・利用先・料金上限が変われば、以前の承認を流用せずSecurity Gateからやり直す。

## 20. 最終実行命令

この仕様書の範囲だけで実装すること。未確認事項を勝手に補完せず、実行していない内容を完成または確認済みと表現しないこと。

無料・ローカルで完結する実装と検査は、最低成功条件まで継続してよい。

ただし、外部サービスへの送信、課金、公開、決済、外部変更、重いクラウド実行は、Security Gate合格後に内容・影響・料金上限を表示し、現在のタスク内で明示承認を得るまで実行してはならない。承認は1回限りであり、条件変更時は再承認を得ること。
