# 限界開発の構築手順

このページは、限界開発をゼロから立ち上げ、最初の案件を公開まで通す実行手順です。

## 0. 先に決める

- 解決したい作業を1つに絞る
- 公開可能範囲を決める
- 最低成功条件を1文で定義する
- 今回作らないものを固定する
- 架空データを用意する
- 最終承認者を人間に固定する

## 1. 最小環境

- スマートフォン
- 対話型AI
- GitHub
- コード作業支援AI
- 実行・テスト環境
- ブラウザ
- 公開先

現在の実例では、iPhone、ChatGPT、Codex、GitHub、Termius、Oracle Cloud Ubuntu、GitHub Pages、note、X、RTSを接続しています。

## 2. 最小リポジトリ

```text
project/
├─ README.md
├─ SAFETY.md
├─ docs/
├─ templates/
├─ episodes/
├─ tools/debug-engine/
└─ index.html
```

## 3. 相談を分解する

1. 入力を確認する
2. 操作手順を確認する
3. 人間の判断を分ける
4. 出力を決める
5. 例外・禁止事項を決める
6. 最低成功条件を固定する

## 4. 仕様を固定する

[仕様書テンプレート](../templates/specification-template.md)で、目的、入力、出力、制約、非対象、最低成功条件、テスト、未確認事項を残します。

## 5. 専用ブランチで実装する

- 変更対象を1機能に絞る
- AIへ仕様書を読ませる
- 変更予定ファイルを確認する
- 差分を確認する
- mainへ直接書き込まない

## 6. UI実装が始まった瞬間にデバッグを接続する

最初の画面または操作ボタンが生えた時点で、[UIデバッグ接続テンプレート](../templates/ui-debug-integration-template.md)を作成します。

- 画面・状態IDを付ける
- ボタン・操作IDを付ける
- 期待接続先を記録する
- スクリーンショットを保存する
- 実測接続先を記録する
- 全体マップを生成する
- 接続が密集したら画面別マップを生成する

UI完成後に後付けするのではなく、UIと同時に台帳を育てます。

## 7. 自動・破壊テスト

- 通常導線
- 連打
- 未選択進行
- 処理中離脱・復帰
- 保存前離脱・復元
- エラー後再実行
- 状態表示と内部状態
- プレビューと最終成果物
- 期待接続先と実測接続先

不具合は再現手順、証拠、期待、実結果を固定してから修正します。修正後は同じテストを回帰テストとして残します。

## 8. 実機確認

- 表示崩れ
- ボタンの押しやすさ
- 誤操作しにくさ
- 次の操作の分かりやすさ
- 状態表示
- 毎回のストレス
- 動画・画像・音声の自然さ

人間確認も前提、操作、観察点、合否条件を記載します。

## 9. リリースゲート

公開直前に次を通します。

1. 共通回帰テスト
2. プロジェクト固有テスト
3. 視覚マップの全体監査
4. 画面別マップの接続監査
5. 人間専用テスト
6. 未確認事項の分離

操作不能、進行不能、データ消失、誤完了、復旧不能、重大な接続不一致があれば公開を停止します。

## 10. 公開と引き継ぎ

- GitHubへ反映
- GitHub Pagesで公開
- テスト結果と未確認事項を記録
- 現在地、残課題、次の一手を引き継ぎ書へ残す
- 同型不具合を共通ナレッジへ昇格する

## 完了条件

- 仕様が残っている
- 最低成功条件が通っている
- 自動テスト結果が残っている
- 視覚マップで接続を監査した
- 人間専用テストを実施した
- 未確認事項が分離されている
- 人間が公開を承認した
