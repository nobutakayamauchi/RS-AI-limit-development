# 限界開発 — 現行開発アーキテクチャ

更新: 2026-08-07

この文書は「限界開発」の定義を書き換えるものではありません。限界開発そのものの定義は固定したまま、社会実験を継続するために現在どのような開発環境・判断系・記録系が生えているかを記録します。

## 限界開発の定義

> **スマートフォン1台しか持たず、精神・肉体・金銭・時間・生活上の問題を抱え、プログラム素人である人間が、AIと根性だけで生活をぶん回す仕組みを作る社会実験。**

技術基盤は主役ではありません。RTS、Vlog Wizard、デバッグエンジン、Obsidian、クラウド、GitHubは、限界状態でも生活と開発を止めないために必要になって生えた生命維持設備です。

## いま何が変わったのか

初期の限界開発は「スマホからAIへ指示し、GitHubとサーバーを操作して作る」が中心でした。現在は、AIへ大量の履歴を丸ごと読ませるのではなく、**何をどのAIへ渡し、何を凍結し、何を実世界の証拠として扱うか**まで設計します。

中心技術はコード生成そのものではなく、**文脈設計・証拠設計・人間判断境界**へ移っています。

## 現在の全体像

```text
人間 / スマートフォン
        ↓
相談・困りごと・アイデア
        ↓
Context Routing
  ├─ project
  ├─ component
  ├─ timing
  ├─ known knowledge / FREEZER
  └─ missing context
        ↓
Human Routing Decision
        ↓
Design Bundle
        ↓
実プロジェクト / 実サーバー
        ↓
Deployment Identity Gate
  ├─ service / unit
  ├─ working directory
  ├─ entrypoint / module
  ├─ active route surface
  └─ deployed revision when available
        ↓
Observation
  ├─ AS_BUILT
  ├─ BROKEN
  ├─ STALE
  └─ UNOBSERVED
        ↓
Debug Link → Lifecycle
        ↓
City Release
        ↓
Human Release Decision
```

## 1. スマホは「実行機」ではなく司令塔

すべての重い処理をスマホ本体で行う必要はありません。スマホから、対話AI、GitHub、SSH、クラウド、ブラウザ、公開先を動かし、判断・確認・再開を一本につなぎます。

重要なのは端末性能ではなく、**どこからでも現在地へ復帰できること**です。

## 2. 文脈設計

長い会話や巨大リポジトリを毎回すべてAIへ渡すと、コスト・混乱・誤認が増えます。そこで情報を役割ごとに分離します。

- 正本となる仕様
- 完了して凍結した知識
- 今回だけ必要な差分
- 実プロジェクトから得た観測
- AIの提案
- 人間の判断
- 未確認事項

AIの性能を上げるだけではなく、**AIが読む世界を設計する**ことを限界開発の重要な実践技術とします。

## 3. RTS / Knowledge Bridge

RTSは限界開発を統制する共通基盤です。現在は、アイデアをそのまま実装へ流さず、ルーティング、設計、実プロジェクト観測、Lifecycle、Release判断までを分離して扱います。

重要な境界:

- routing decision は人間が持つ
- observation は証拠であり、自動修復命令ではない
- common UI はレビュー面であり、勝手に編集・修復する面ではない
- screenshot / sketch は入力アダプターであり、自律的な設計権限ではない
- implementation / approval / release は自動で越境しない

## 4. Deployment Identity

実dogfoodで、古いソースツリーを見て実稼働と誤認しかける問題が見つかりました。そのため現在は、runtime realityを分類する前にDeployment Identityを確定します。

> **Deployment Identity MUST be established before runtime implementation classification.**

> **Code existence != runtime evidence.**

コードが存在するだけでは、今それが動いている証拠にはなりません。

## 5. Observation First

実装候補を見つけても、存在だけで `AS_BUILT` や `BROKEN` と決めません。実際に観測できたものだけを分類します。

- `AS_BUILT`: 実装・稼働を証拠で確認
- `BROKEN`: 対象runtimeで壊れている証拠あり
- `STALE`: 古い・非稼働・重複した実装やUI
- `UNOBSERVED`: まだ確認していない

未確認を成功へ塗り替えないこと自体が、限界開発の品質です。

## 6. デバッグエンジン

UI操作、不具合、誤操作、復帰、ストレスを再現可能なテスト資産へ変換します。一度踏んだ問題を、人間が何度も体当たりで踏み直さなくてよい形へ寄せます。

視覚ナビゲーションマップは画面と操作の接続を可視化します。ただし、静的な画面やコードの存在とruntime realityを混同しません。

## 7. Obsidian / FREEZER

ObsidianやFREEZERは、知識を全部一つの巨大文脈へ詰めるためではなく、完了した判断・仕様・学習を凍結し、必要な時だけ再利用するための記憶層です。

現在の方針は「全面自動書き換え」ではありません。知識候補を抽出し、適切な場所へルーティングし、人間の判断境界を保ちます。

## 8. GitHub

GitHubはコード置き場だけではありません。

- 仕様の正本
- ブランチ単位の実験
- PRでの差分レビュー
- テストと証拠
- 完了記録
- GitHub Pagesによる公開入口
- 中断後の再開地点

を保持します。

## 9. 成功条件

現在の限界開発では、「コードができた」を完成条件にしません。

- 何を作るかが分離されている
- 実稼働のIdentityが分かる
- 確認済みと未確認が分かれる
- 失敗が再現可能な知識へ変換される
- AIが勝手に人間判断を越えない
- 中断しても再開できる
- 最終的に生活・仕事・収入・生存へ接続できる

ここまで含めて、開発環境です。

## 10. 変えないもの

環境がどれだけ巨大化しても、限界開発の主語は変えません。

**すごいシステムを作ることが目的ではない。**

制約だらけの人間が、必要な道具・技術・判断方法をその場で獲得し、生活を一日でも長く、自分の手で回せるようにする。その社会実験が限界開発です。
