# 限界開発 構築手順

更新: 2026-08-07

この手順は「巨大な限界開発環境を最初から全部作る」ためのものではありません。

限界開発では、必要になった機能だけを増やし、いつでもスマホから再開できる状態を先に作ります。

## 0. 先に定義を固定する

限界開発とは、

> **スマートフォン1台しか持たず、精神・肉体・金銭・時間・生活上の問題を抱え、プログラム素人である人間が、AIと根性だけで生活をぶん回す仕組みを作る社会実験。**

RTSやデバッグエンジンを作ること自体を目的化しない。

## 1. 最小司令塔を作る

最低限必要なのは次です。

- スマートフォン
- 対話AI
- GitHubアカウント
- ブラウザ
- 必要ならSSHできるターミナル

ローカルPCを必須条件にしません。

## 2. Source of TruthをGitHubへ置く

最初に決めるもの:

- README / 企画の定義
- 仕様書
- 安全基準
- 現在の作業ブランチ
- 完了記録

会話だけを正本にしない。チャットが長くなったり途切れたりしても、GitHubから再開できる状態を作ります。

## 3. 問題を小さく切る

「生活を全部自動化する」ではなく、今困っている一件を切ります。

例:

```text
困りごと
↓
対象プロジェクト
↓
対象コンポーネント
↓
今日必要か / 後でよいか
↓
確認が必要な事実
```

ここから先が現在の文脈設計です。

## 4. Context Routingを行う

AIへ全履歴を丸ごと渡さず、今回必要なものだけを集めます。

分離する対象:

- 現在の要求
- 既存仕様
- 凍結済み知識
- 実プロジェクト情報
- 未確認事項
- AI提案
- 人間判断

必要になった時だけRTS / Knowledge Bridge / FREEZER / Obsidianを使います。

## 5. Designを実装と分ける

設計Bundleや実装候補が出ても、自動実装しません。

まず確認する:

- 何を直すのか
- どこへ入れるのか
- 既存責務を壊さないか
- regression targetはあるか
- migrationが必要か
- 人間が今やると決めたか

## 6. 実プロジェクトへ接続する

デモではなく、実際に使っているプロジェクトをDogfood対象にします。

ここで最重要なのがDeployment Identityです。

### runtimeを分類する前に確認

- service / unit
- working directory
- entrypoint / loaded module
- active routes / runtime surface
- deployed revision when available

> **Code existence != runtime evidence.**

古いcloneや未deploy branchを見つけても、それだけで実稼働とは判定しません。

## 7. 観測を記録する

planned itemごとに、実際に確認できたものだけを記録します。

```text
AS_BUILT   実装・稼働を確認
BROKEN     対象runtimeで故障を確認
STALE      古い・非稼働・重複
UNOBSERVED 未確認
```

「たぶん動く」はAS_BUILTではありません。

## 8. デバッグを資産化する

不具合を踏んだら、可能な限り次を残します。

- 再現手順
- 対象Deployment Identity
- 入力
- 期待結果
- 実結果
- 画面 / ログ / route / code evidence
- 修正
- regression test

再発時に人間が最初から調べ直さない形へ寄せます。

## 9. Lifecycleへ戻す

RTSを使う場合は、Design BundleとObservationをDebug Linkで接続し、Lifecycleへ戻します。

未観測やSTALEが残っていても、消したふりをしません。

City Releaseは次の判断材料を作りますが、勝手にreleaseしません。

## 10. 完了を凍結する

一区切りついたら、

- 何が完了したか
- 何がknown issueか
- 何が未観測か
- 次に何をしないか
- 次回どこから始めるか

をCompletion Recordとして残します。

これが「再開可能性」の核です。

## 11. 公開する

GitHub Pages / README / docsへ、社会実験として分かる形で公開します。

公開時は、内部ツールを主役にしすぎない。

中心メッセージは常に、

> 制約のある人間が、AIを使って生活を回す方法を獲得できるか

です。

## 12. 増築判断

新しい基盤を作る前に、次を確認します。

- 今の詰まりを直接減らすか
- 実プロジェクトで使う予定があるか
- 既存ツールで代替できないか
- 作った後に保守できるか
- 本筋を止めてシムシティ化していないか

「便利そう」だけでは増築しません。

## 最小完成条件

限界開発環境の最小完成は、ツール数ではなく次で判定します。

1. スマホから現在地が分かる
2. 正本がGitHub等に残る
3. 実プロジェクトへ到達できる
4. 実稼働のIdentityを確認できる
5. 確認済みと未確認を分けられる
6. 失敗を再現可能な記録へ変えられる
7. 中断後に再開できる
8. 最後の判断を人間が持てる

ここから先のRTS、Knowledge Bridge、デバッグエンジン等は、必要性に応じて育てます。
