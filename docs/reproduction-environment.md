# 限界開発を再現するための環境と前提条件

このページでは、限界開発と同じような開発環境・進め方を再現したい人向けに、必要な道具、役割分担、基本構成、注意点をまとめます。

限界開発は、すべての処理をスマートフォン本体だけで実行する方法ではありません。

スマートフォンを操作端末として使い、AI、GitHub、Codex、RTS、GitHub Pages、note、Xなどを一つの開発フローとして接続する方法です。

---

## 1. 必要なもの

最低限、次の環境が必要です。

- スマートフォン
- GitHubアカウント
- AIチャット環境
- GitHubへ接続できる開発支援環境
- Webブラウザ
- 文章・画像を公開する場所
- インターネット接続

---

## 2. 推奨する構成

### 操作端末

- iPhoneまたはAndroidスマートフォン
- SafariまたはChrome
- GitHub公式アプリまたはブラウザ版GitHub

### AI

- 要件整理・仕様化・文章作成を行うAI
- コード生成・修正・レビューを行うAI
- 必要に応じて画像生成AI

### 開発・管理

- GitHub
- GitHub Pages
- Codexなどのコード作業支援
- RTSまたは同等の仕様・ログ・評価管理基盤

### 発信

- X
- note
- GitHub Pages
- 必要に応じて配信サービス

---

## 3. 役割分担

限界開発では、すべてをAIへ丸投げしません。

### 人間が行うこと

- 何に困っているかを決める
- 公開してよい範囲を判断する
- 最低成功条件を決める
- 実際に動いたか確認する
- 本番利用してよいか判断する
- 公開内容を承認する

### AIが行うこと

- 問題の分解
- 要件整理
- 仕様書作成
- 実装案作成
- コード生成
- テスト案作成
- ドキュメント作成
- 改善案の提示

---

## 4. 基本フロー

1. 困っている作業を一つ決める
2. 公開可能な情報だけに切り分ける
3. 現在の業務を分解する
4. 最低成功条件を決める
5. 仕様書を作る
6. 専用ブランチで実装する
7. 架空データでテストする
8. スマートフォンで実機確認する
9. 確認済み事項と未確認事項を分ける
10. GitHub Pagesまたはリポジトリで公開する
11. note・Xで記録を残す
12. 次の改善へつなげる

---

## 5. 再現時の重要条件

限界開発を再現するために重要なのは、同じAIや同じ端末を使うことではありません。

重要なのは、次の条件を守ることです。

- 問題を一つに絞る
- 最低成功条件を先に決める
- 実在データを持ち込まない
- 未確認事項を事実として扱わない
- 試作品と本番利用を区別する
- 判断記録を残す
- 失敗と修正も記録する
- 人間が最終承認する

---

## 6. RTSとの関係

RTSは、限界開発を回すための共通基盤です。

主に次の役割を持ちます。

- 仕様管理
- 判断記録
- ガバナンス
- 実行制御
- テスト記録
- リスク確認
- 引き継ぎ
- 学習結果の蓄積

RTSを使わなくても同じ流れは再現できますが、その場合は同等の記録・承認・安全確認の仕組みを自分で用意する必要があります。

---

## 7. 再現しやすい最小構成

最初から大きな環境を作る必要はありません。

最小構成は次の通りです。

- スマートフォン
- GitHub
- AIチャット
- 1つのREADME
- 1つの仕様書
- 1つのテスト記録
- 1つの試作品
- 1つの公開ページ

まず一案件だけ、この構成で最後まで通すことを推奨します。

---

## 8. 向いている人

- プログラミング未経験だが、業務改善を形にしたい人
- スマートフォン中心で開発を進めたい人
- AIを使って小さな仕組みを作りたい人
- 完成品だけでなく、開発過程も残したい人
- 個人または小規模で運用したい人

---

## 9. 向いていないケース

- 機密情報を公開環境へ持ち込みたい
- 人間確認なしで自動実行したい
- 最初から本番品質を保証したい
- 大規模組織の基幹システムをすぐ作りたい
- 要件が定まっていないまま実装だけ進めたい
