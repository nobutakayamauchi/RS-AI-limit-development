# Token Wallet / Cost Router — Core Specification

Date: 2026-08-16
Status: `CORE_INVARIANT / V0_REQUIRED`
Tracking: Issue #10

## Why this is core

The business is not merely “host a replacement for GPT distribution.” The durable problem is:

> **Who is financially authorized to pay for this inference, and how much are they allowed to spend before execution begins?**

ChatGPT subscription billing and API billing are separate. A user having a paid ChatGPT subscription does not pay the API cost generated by this service.

Therefore payer resolution is a runtime authorization boundary, not a later billing feature.

## Hard invariant

```text
NO PAYER RESOLUTION
→ NO BUDGET AUTHORIZATION
→ NO MODEL EXECUTION
```

Every provider call must be attributable to an authorized payer context before the request is sent.

## V0 payer modes

Only two modes are required for the first Dogfood/product boundary.

### 1. BYOK

`BYOK = Bring Your Own Key`

The end user supplies a provider credential and the provider bills that user directly.

V0 rules:

- the key is never committed to Git;
- the key is never embedded in public app JavaScript;
- the key must not be written to ordinary application logs;
- persistence is NOT required in v0;
- prefer session-scoped use; persistent key storage requires a separate encrypted-secret design and authentication gate;
- the application may meter estimated/observed usage for UX and diagnostics, but must not debit platform credits for provider inference cost;
- application/service fees, if any, are a separate commercial concept from provider inference cost.

### 2. PLATFORM_CREDIT

The platform/creator has intentionally funded a bounded amount of inference.

V0 rules:

- there is no unlimited public free mode;
- every funded app/session has an explicit hard budget or request cap;
- execution stops before the next request when the authorized budget is exhausted;
- v0 credit can be operator-granted Dogfood/promotional credit; selling stored prepaid value is deferred until payment/legal design is reviewed;
- credit authorization and actual provider spend are separate records.

## Future payer modes

Not required for v0 execution, but the schema must permit them without rewriting the inference path.

```text
USER_WALLET      # prepaid service credits purchased by end user
CREATOR_PAYS     # creator budget pays for users of one package
SPONSORED        # campaign/sponsor budget pays
HYBRID           # creator pays first N / threshold, then user wallet/BYOK
```

## Execution pipeline

```text
REQUEST
  ↓
APP / PACKAGE POLICY
  ↓
PAYER RESOLUTION
  ↓
CREDENTIAL RESOLUTION
  ↓
BUDGET AUTHORIZATION
  ↓
MODEL / EFFORT ROUTING
  ↓
MAX-COST GUARD
  ↓
PROVIDER EXECUTION
  ↓
OBSERVED USAGE
  ↓
COST CALCULATION
  ↓
LEDGER / METER EVENT
  ↓
REMAINING BUDGET
  ↓
RESPONSE
```

A provider call is invalid if payer resolution or budget authorization was bypassed.

## Package policy schema

Example:

```json
{
  "billing": {
    "allowed_payer_modes": ["BYOK", "PLATFORM_CREDIT"],
    "default_payer_mode": "BYOK",
    "platform_credit": {
      "enabled": true,
      "budget_id_env": "MIGRATION_FIXTURE_BUDGET_ID",
      "hard_limit_usd_micros": 500000
    }
  },
  "routing": {
    "policy": "cost_aware_v0",
    "default_tier": "LUNA",
    "allowed_tiers": ["LUNA", "TERRA", "SOL"],
    "max_tier": "SOL"
  }
}
```

Use integer micros (or another explicit fixed-point unit), not floating-point currency, for ledger values.

## Payer context

Every execution should resolve an internal object equivalent to:

```text
payer_mode
payer_id / budget_id
credential_source
currency
remaining_budget
request_budget
package_id
session_id
pricing_version
```

No API key should be included in normal usage/audit events.

## Budget authorization

Authorization occurs before provider execution.

At minimum evaluate:

- payer mode allowed by package;
- credential available for chosen payer mode;
- account/budget active;
- hard request/input/history limits;
- model tier allowed;
- requested/estimated maximum cost fits remaining budget;
- package/app hard cap not exhausted;
- rate/abuse limit not exhausted.

Failure is explicit and provider execution does not occur.

## Actual-cost accounting

After a provider response:

1. collect provider-reported usage where available;
2. bind it to exact provider/model/pricing-version;
3. calculate actual provider cost;
4. write an immutable usage/meter event;
5. debit the authorized platform budget only for modes where the platform is payer;
6. preserve estimated vs actual cost separately.

If cost cannot be established, record `COST_UNKNOWN` rather than silently treating the request as free.

## Pricing registry

Pricing is external mutable state.

Hard rules:

```text
MODEL NAME != PRICE
CURRENT PRICE != HISTORICAL PRICE
MISSING PRICE != ZERO COST
```

Each pricing entry must record:

- provider
- model ID
- effective timestamp/date
- input price
- cached-input price where applicable
- output price
- special long-context/mode rules if relevant
- evidence/source URL or source identifier
- observed/reviewed timestamp

Do not make business logic depend on one permanently hard-coded price.

## Cost-aware model routing

Cost control and quality control share one decision boundary.

Possible progression:

```text
Luna
  ↓ confidence / complexity gate
Terra
  ↓ material uncertainty / high consequence gate
Sol
  ↓ only if justified
DA / WITNESS-like / METEOR validation
```

The router must optimize for the protected outcome, not merely cheapest-token selection.

Rules:

- cheapest capable tier wins when quality evidence supports it;
- escalation requires a reason code;
- package may cap the highest model tier;
- payer budget may cap or reject escalation;
- expensive validation passes run only when required by workload/risk policy;
- routing decisions and spend are observable together so quality-per-dollar can be measured.

## Ultimate Loop connection

The Cost Router is not Ultimate Loop itself. Ultimate Loop supplies the development/evaluation method used to test competing routing policies.

A routing policy must be replaceable through METEOR/DARWIN when a cheaper or stronger model/provider appears.

Protected outcome:

> acceptable task quality under an explicit authorized cost/risk envelope.

## Ledger/event minimum

V0 does not need a full accounting system, but every platform-funded provider call should be able to produce a record equivalent to:

```json
{
  "event": "inference_usage",
  "package_id": "migration-fixture-ai",
  "payer_mode": "PLATFORM_CREDIT",
  "budget_id": "dogfood-001",
  "provider": "openai",
  "model": "gpt-5.6-luna",
  "pricing_version": "openai-2026-07-30",
  "input_tokens": 0,
  "cached_input_tokens": 0,
  "output_tokens": 0,
  "estimated_cost_usd_micros": 0,
  "actual_cost_usd_micros": 0,
  "result": "SUCCESS"
}
```

Do not log provider API keys or raw customer-private Knowledge in the billing event.

## V0 completion conditions

The billing/cost core passes v0 only when:

1. every provider call resolves one payer mode first;
2. BYOK can execute without consuming platform inference budget;
3. PLATFORM_CREDIT cannot execute after its hard budget/cap is exhausted;
4. a request cannot select a disallowed expensive model directly;
5. usage is associated with model + pricing version;
6. missing price/usage becomes explicit unknown/error, never zero;
7. provider/API failure does not incorrectly debit successful usage;
8. concurrent/repeated requests cannot trivially overspend the same remaining budget;
9. Dogfood shows the platform does not expose an unlimited unauthenticated platform-paid inference path.

## Roadmap

### v0

- payer abstraction in core
- BYOK session path
- PLATFORM_CREDIT bounded path
- price registry
- pre-execution budget authorization
- simple model-tier policy
- usage/meter events
- hard stop

### v1

- purchased prepaid wallet
- user-visible usage meter
- package-level limits
- stronger automatic model routing
- idempotent/transactional ledger

### v2

- monthly plans
- CREATOR_PAYS
- USER_WALLET
- SPONSORED
- HYBRID payer priority/fallback
- creator revenue share

## Business rule

Do not launch an unauthenticated, unlimited, platform-funded inference endpoint.

The default economic posture is:

> **The person/entity benefiting from or sponsoring inference has an explicit bounded payer identity before execution.**
